# WireView 真扩展屏路径

## 目标

让 Windows 把平板识别为一块独立显示器。应用窗口可被拖到该显示器，平板只接收这块虚拟屏的画面；这与当前复制 `DISPLAY1` 的镜像路径不同。

## 已开始的部分

`WireViewIddDriver` 现在以平板实际验证过的模式申报无 EDID 虚拟显示器：

- 2560x1600@60（首选，清晰与长期稳定档）
- 1920x1200@120（高刷新档）
- 1920x1200@60（兼容档）

Windows 会把“显示器申报”和“实际帧传输”分开处理；只有驱动加载且显示器启用后，才会把这些模式提供给显示设置。

驱动与 Host 已共享 `windows/common/idd_frame_relay.hpp` 的 v1 中继协议，并有独立单元测试。协议严格定义了流描述、三个共享纹理槽位、帧就绪、帧释放和停止消息；控制数据只走本机命名管道，像素始终留在 D3D11 共享纹理中。Host 管道 ACL 仅允许当前所有者、LocalSystem 和 LocalService（UMDF）连接；驱动的协商线程不会阻塞 IddCx 交换链。

Host 已完成三槽共享纹理的实际验证：用 `D3D11_RESOURCE_MISC_SHARED_NTHANDLE` 与 `D3D11_RESOURCE_MISC_SHARED_KEYEDMUTEX` 创建三张 BGRA 纹理，跨 D3D11 设备按 LUID 打开后核对尺寸与格式。纹理由 Host 以随机 `Global\\WireViewIdd-*` 名称创建，并使用仅允许当前所有者、LocalSystem 和 LocalService（UMDF）的 ACL；创建句柄会随中继会话保留。驱动不再要求把进程句柄复制到另一身份，而是只接受该命名前缀、逐槽核对属性后用 `OpenSharedResourceByName` 打开，最后回传 `textures_ready`。本机命名管道回归测试已经对三槽真实 D3D11 命名资源完成这套往返验证。

键控同步的约定仍是驱动仅在 key 0 可得时复制并交出 key 1；Host 消费后交还 key 0。任一槽位未归还时该帧直接丢弃，不等待。驱动现在在交换链线程中只执行零等待 GPU `TryCopy`，把成功复制的槽位和单调序号放进最多三条的后台队列；中继线程单独发送 `frame_ready`，核对 `frame_released` 后再继续。Host 会保持纹理到会话结束、取得 key 1、校验序号并归还 key 0。真实 D3D11 命名纹理回归会连续发布六帧并验证整个往返闭环。

当前 Host 的中继监听器只执行帧消费与同步验证，还没有把已取得的纹理接入现有 H.264 编码器；因此它不是一条可显示画面的扩展屏数据面。

## 帧路径设计

```text
Windows 桌面合成器
  -> IddCx 虚拟显示器交换链
  -> UMDF 驱动的快速 GPU 复制（多缓冲、不得阻塞）
  -> 受限本机帧中继
  -> WireView Host 的 NV12 / H.264 / USB 链路
  -> Android MediaCodec Surface
```

驱动不直接调用 ADB、不直接管理 Android 连接，也不在交换链循环中等待编码或 USB。它只持有 IddCx 帧到完成一次 GPU 复制的极短时间；Host 进程复用已验证的编码、重连、输入和遥测逻辑。这符合 IddCx 对快速交换链处理的要求，也隔离了驱动崩溃风险。

## 接下来的实现顺序

1. 把 Host 已取得的中继纹理接入硬件编码器输入，并保留帧时间戳和背压统计。
2. 把 Host 的输入源抽象为“DXGI 复制”或“IddCx 中继”，使 H.264、USB、Android 无需重写。
3. 为驱动中继补齐断线后在新交换链上重建的会话恢复。
4. 在隔离测试机或获得微软认可签名后加载驱动，启用 Windows 扩展模式，核对模式、帧率、鼠标/笔坐标和拔插恢复。
5. 完成发布签名与安装体验后，才把该路径提供给主力机日常使用。

## 当前限制

本机 Secure Boot 保持开启。现有本地自签名驱动可以构建、校验和暂存，但会被 Windows 生产内核信任策略阻止加载；因此不能在这台主力机上让虚拟显示器真正出现。这个限制不影响现在编译帧中继和 Host 抽象，也不会通过关闭 Secure Boot 或改启动项绕过。
